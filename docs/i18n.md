# Internationalisation (i18n)

Objectif : l'application s'adapte automatiquement à la langue de l'utilisateur, partout dans le monde.
Langues prises en charge : français (`fr`, langue source), anglais (`en`), arabe (`ar`, de droite à gauche), espagnol (`es`), portugais (`pt`).

**État :** phase A (moteur) terminée. Phase B en cours : groupe 1 (accueil, connexion, inscription, mot de passe oublié) et groupe 2a (tableau de bord expéditeur, envois, détail d'un envoi, suivi, notifications) branchés ; groupe 2b (création d'envoi, paiement, profil, réclamations) branché ; groupe 3 (GP) à faire. Plan complet : A moteur, B application (par groupes de pages), C backend (erreurs et notifications), D site vitrine (faite), E contrôle qualité.

| Page | Langues branchées |
|---|---|
| `index.html` (accueil, choix du profil) | fr, en, ar, es, pt |
| `connexion.html`, `inscrire.html`, `oublie.html` | fr, en, ar, es, pt |
| `pwa.js` (bannière d'installation, notifications) et bouton Google (`gauth.js`) | fr, en, ar, es, pt |
| `dashexpediteur.html`, `envois.html`, `detailenvoi.html`, `suivi.html`, `notifications.html` (aussi côté GP) | fr, en, ar, es, pt |
| `creenvoi.html` (+ `page-creenvoi.js`), `paiement.html`, `profile.html`, `reclamation.html` | fr, en, ar, es, pt |
| `geo.js` (sélecteur de pays : continents, pays par `Intl.DisplayNames`, pluriels) | fr, en, ar, es, pt |
| Autres pages | français seulement (moteur non chargé) |

**Pas de sélecteur de langue flottant dans les pages de l'application** (tableau de bord, envois, suivi…) : il masquerait l'avatar. La langue se choisit sur les pages de connexion et dans **Profil › Langue** (cinq langues, choix mémorisé). Wolof est affiché comme « Bientôt ».

Les messages d'erreur renvoyés par l'API (`error`, `message`) sont traduits côté serveur (phase C, voir « Phase C : traduction côté serveur ») ; sans en-tête de langue pris en charge, le message d'origine est conservé.

## Choix de la langue

Dans cet ordre (`frontend/i18n.js`, `resolveLanguage`) :

1. Le choix de l'utilisateur, mémorisé dans `localStorage` (`sengpLang`).
2. La langue de l'appareil (`navigator.languages`), si elle est prise en charge. Exemple : `pt-BR` donne `pt`.
3. Sinon, la langue du pays déduit du **fuseau horaire** (`Intl`). Exemple : un appareil en allemand à `Europe/Madrid` donne `es`. La table `COUNTRIES` couvre les pays francophones, arabophones, hispanophones et lusophones.
4. Sinon, l'anglais.

Aucune adresse IP n'est lue et aucun service externe n'est appelé. Conséquence assumée : un téléphone réglé en anglais, utilisé au Sénégal, reste en anglais tant que l'utilisateur n'a pas choisi une autre langue. Le sélecteur de langue (`SengpI18n.mountSwitcher(élément)`) permet de changer à tout moment.

Un fuseau absent de la table (par exemple `Asia/Tokyo`) ne déclenche aucune erreur : on retombe sur l'anglais. Pour ajouter un pays dont la langue est prise en charge, compléter `COUNTRIES` (le test vérifie la langue et l'unicité des fuseaux).

## Utiliser le moteur dans une page

```html
<script src="api.js"></script>
<script src="i18n.js"></script>

<h1 data-i18n="home.title">Bienvenue</h1>
<input data-i18n-attr="placeholder:common.search; title:common.close" placeholder="Rechercher">
```

```js
sengpT('errors.generic');                     // texte brut
sengpT('errors.expediteur_only', { type: 'GP' });
sengpT('mission.count', { count: 3 });        // pluriel
SengpI18n.fmt.currency(15000);                // « 15 000 FCFA » (chiffres latins dans toutes les langues)
SengpI18n.fmt.date(m.created_at);             // date selon la langue
SengpI18n.fmt.dateTime(m.created_at);
SengpI18n.lang;  SengpI18n.dir;               // 'ar' / 'rtl'
await SengpI18n.ready;                        // traductions appliquées
window.addEventListener('sengp:languagechange', ...);
```

Règles :

- Le texte écrit dans la page reste le **français** : c'est la valeur par défaut tant que les traductions ne sont pas chargées, et la page reste lisible hors ligne ou si un dictionnaire ne se charge pas.
- Les traductions sont insérées comme **texte** (`textContent`), jamais comme HTML. Une valeur ne doit pas contenir `<` ni `>` (un test l'impose). Pour du texte structuré, découper en plusieurs clés.
- Une clé absente d'une langue retombe sur l'anglais, puis sur le français, puis s'affiche telle quelle (et apparaît dans `SengpI18n.missing`).
- Le nom `sengpT` (et non `t`) évite toute collision avec les variables locales des pages.
- Les montants restent en **FCFA** (paiements Wave et Orange Money). Seuls les séparateurs et les dates changent selon la langue.

## Fichiers de langue

`frontend/locales/<langue>.json`, à plat : `"section.cle": "texte"`.

- Nommer par écran puis par usage : `home.title`, `payment.method.cod`, `errors.network`.
- Variables : `{nom}`. Elles doivent être identiques dans toutes les langues (sauf formes de pluriel : voir ci-dessous).
- Pluriels : `cle.one`, `cle.other`, et pour l'arabe `zero`, `one`, `two`, `few`, `many`, `other`. Les formes numérotées peuvent omettre `{count}` quand le nombre est implicite (« شحنة واحدة »). `cle.other` est obligatoire dans chaque langue.
- Après modification : `cd frontend && npm test`. Les tests vérifient que les cinq langues ont les mêmes clés, que les variables correspondent, que les pluriels sont complets (0 à 200) et que chaque statut de mission de la base a sa traduction.

### Ajouter une langue

1. Créer `locales/<code>.json` avec toutes les clés du français.
2. Ajouter le code à `SUPPORTED`, `NATIVE_NAMES` et `LOCALE_TAGS` dans `i18n.js`, ainsi que les pays dans `COUNTRIES`.
3. Si la langue s'écrit de droite à gauche, l'ajouter à `RTL`.
4. Compléter `tests/i18n.test.js` si besoin.

## Brancher une page (procédure de la phase B)

1. Dans `<head>` : `<script src="api.js">`, puis `<script src="i18n.js">`, puis `<link rel="stylesheet" href="i18n.css">`.
2. Ajouter `data-i18n="cle"` aux éléments de texte, `data-i18n-attr="placeholder:cle; aria-label:cle"` aux attributs. Le texte français reste dans la page.
3. Phrase avec lien dont l'ordre varie : `<span data-i18n-rich="cle">Texte {lien}</span>` avec, à l'intérieur, l'élément portant `data-slot="lien"` (et son propre `data-i18n`). Le modèle de la clé contient `{lien}`.
4. Dans les scripts : `sengpT('cle', { variable })` à la place des textes en dur. Pour un libellé modifié par le script (bouton, texte d'état), mémoriser aussi sa clé avec `el.setAttribute('data-i18n', cle)` : il suit alors un changement de langue.
5. Ajouter `<div data-i18n-switcher></div>` pour le sélecteur de langue.
6. Ajouter le bloc `[dir="rtl"] …` : éléments positionnés en absolu (`left`/`right`), `padding`/`margin` d'un seul côté, flèches (`transform: scaleX(-1)` ou classe `i18n-flip`).
7. Les tests `tests/pages-i18n.test.js` vérifient ensuite : clés présentes dans les cinq langues, texte français de la page identique à `fr.json`, syntaxe des scripts, plus aucun `alert()` en français en dur.

Les captures d'écran de contrôle se font en navigateur sans écran : `msedge --headless=new --lang=ar --window-size=500,900 --screenshot=… http://localhost:8766/connexion.html` (largeur minimale 500 px).

## Outil d'extraction automatique

`autoi18n.py` (usage interne, pas dans le dépôt) marque les éléments de texte simples d'une page (`data-i18n`, `data-i18n-attr`) et liste les phrases à traduire. Il a servi pour `creenvoi.html`. Les éléments dont le **script** modifie le texte (étape, libellé du bouton, états) ne doivent pas garder de `data-i18n` figé dans la page : le script pose la clé avec `setI18n(élément, clé)` pour que le texte suive un changement de langue.

## Pays, dates et montants

- Les pays sont **enregistrés en français** (ex. `Sénégal`) : c'est la valeur stockée par l'API. Pour l'**afficher**, utiliser `SengpGeo.displayCountry(nomFrancais)` (nom du pays par `Intl.DisplayNames` dans la langue courante). Les villes restent telles que saisies.
- Dates et heures : `SengpI18n.fmt.date(d, options)`, `fmt.dateTime(d)`, `toLocaleTimeString(SengpI18n.fmt.localeTag(), …)`. Ne plus écrire `'fr-FR'` en dur.
- Montants : `SengpI18n.fmt.currency(n)` (chiffres latins, FCFA). Les montants calculés ou payés ne changent jamais.
- **Données enregistrées** : le type de colis envoyé à l'API reste le libellé **français** (l'écran affiche la traduction). Les noms de pays le sont aussi (voir plus haut).
- Les **notifications et messages d'erreur renvoyés par l'API** (titres, textes) sont traduits côté serveur (phase C). Restent en français : console d'administration, messages des validateurs (express-validator), alertes aux administrateurs, anciennes notifications déjà enregistrées.

## Droite à gauche (arabe)

Le moteur pose `lang` et `dir="rtl"` sur `<html>` dès la détection. La mise en page des pages (marges, alignements, icônes directionnelles) reste à adapter page par page avec des propriétés logiques CSS (`margin-inline-start`, `text-align: start`…) : c'est un travail de la phase B, à vérifier visuellement.

## Phase C : traduction côté serveur

- Le frontend envoie `Accept-Language` (langue de l'application) sur chaque appel à l'API (`api.js`). Le serveur (`backend/src/i18n`) en déduit la langue de la requête ; en-tête absent ou langue non prise en charge : message d'origine inchangé.
- Messages d'erreur : catalogue `ERRORS` dans `backend/src/i18n/messages.ts`, clé = message d'origine, 5 langues. Un message absent du catalogue reste tel quel. Pour en ajouter un : l'inscrire dans `ERRORS` (ou `PATTERNS` s'il contient une valeur).
- Langue du compte : colonne `users.language` (fr/en/ar/es/pt, nullable), renseignée à l'inscription, modifiable par `PUT /users/me {language}`, renvoyée par `GET /users/me` et à la connexion. Un choix explicite dans le sélecteur est enregistré automatiquement ; la détection automatique ne l'est pas.
- Notifications : créées avec un modèle (`TEMPLATES`) et des paramètres, rendues dans la langue enregistrée du destinataire (français par défaut). Les montants sont formatés par langue, chiffres latins. Le modèle et les paramètres sont gardés dans `metadata`.
- Hors périmètre : console admin (français), alertes admin, messages des validateurs, anciennes notifications, push de diffusion admin.

## Phase D : site vitrine (`website/`)

Le site est statique et multilingue (fr, en, ar, es, pt). Le **français reste la source unique** : les pages de `src/pages/` ne sont pas dupliquées. Le build (`website/build.mjs`) génère une version par langue : `/` (français), `/en/`, `/ar/`, `/es/`, `/pt/`.

- **Traductions** : `website/src/locales/<langue>.json`, dictionnaire plat « segment français → traduction ». Un segment est un bloc de texte avec ses balises de mise en forme numérotées (`<a1>…</a1>`, `<b2>…</b2>`) ; les attributs `alt`, `title`, `aria-label`, `placeholder` et la description des pages sont traduits par leur valeur. Les liens, classes et attributs viennent du HTML français.
- **Ajouter ou modifier un texte** : modifier la page française, puis `npm run extract` (régénère `src/locales/_segments.json`), traduire les segments nouveaux (`node scripts/i18n-tool.mjs list` / `merge <langue> <fichier>`), puis `npm run i18n:check`. Toute traduction manquante laisse le français et est signalée par le build ; `build:live` refuse de publier tant qu'il en manque.
- **Pages juridiques** (mentions légales, confidentialité, conditions) : uniquement en français (`"i18n": false` dans leur en-tête). Depuis les autres langues, les liens y mènent avec « (en français) » et `hreflang="fr"`.
- **SEO** : `lang`/`dir` sur `<html>`, `rel="alternate" hreflang` pour chaque langue + `x-default` (français), `canonical` propre à chaque langue, `og:locale`, sitemap avec alternates (build de production).
- **Choix de la langue** (`src/js/lang.js`) : un clic sur le menu de langue est mémorisé ; sur une page française sans choix mémorisé, langue de l'appareil, puis pays déduit du fuseau horaire (même table que l'application), puis anglais, avec une seule redirection vers la même page. Aucune redirection depuis une page déjà localisée, au retour arrière ni pour les robots.
- **Arabe** : `dir="rtl"` et `src/css/rtl.css` (miroir des positions physiques). Chiffres latins conservés.
- **Textes dans le JavaScript** : aucun ; les libellés lus par `site.js`/`home.js` viennent d'attributs de la page (`data-label-open`, `data-title`, `data-cities`).
- **Tests** : `cd website && npm test` (analyseur HTML, localisation, build des 5 langues, hreflang, choix de la langue).

### Limites connues de la phase D
- Les adresses restent en français (`/en/comment-ca-marche/`) : pas de slugs traduits.
- Les captures de l'application (`assets/app/*.webp`) sont en français ; à régénérer par langue avec `scripts/shoot-app.mjs`.
- La page 404 n'existe qu'en français.
- Traductions automatiques, non relues par des locuteurs natifs (points signalés : « voyageur (GP) » rendu « مسافر (GP) » et « ناقل (GP) » selon les pages en arabe ; « gros porteur » laissé en français dans la FAQ ; noms de villes translittérés en arabe).
- Le site reste en mode relecture (non indexable) tant que `live` et `legalReviewed` valent `false`.

## Textes juridiques

Les CGU, la politique de confidentialité et les mentions légales ne sont **pas** traduits tant qu'un juriste n'a pas validé chaque langue. Ils restent en français, avec un bandeau d'explication.
